# Concept Brief: gttp UI/UX Redesign

## Problem

The site (gttp.mooseflip.com) works but its visual design is dated/generic: a
plain horizontal list of book cards, system default sans-serif stack, a single
inline `<style>` block with minimal visual hierarchy, no manual theme control,
and no motion/interaction polish. The user wants a UI/UX designer's review
pass to bring it up to current design standards.

## Goal

Redesign the generated static site to look clean, modern, and current —
applying rising UI trends — while keeping it a fast, dependency-free static
site (no framework, no build step beyond the existing Python generator).

## In scope

- Full visual redesign of the shared HTML shell / CSS in
  `src/gttp/publish.py` (`_HTML_SHELL` and the render functions that build
  class names/markup): typography, color system, spacing, cards, buttons,
  focus states, micro-interactions/transitions.
- **Layout rework is allowed**: the index page may move away from the current
  horizontal list to a more current layout (e.g. a responsive grid/bento
  layout of cover cards) if that reads as cleaner than the list. Book detail
  page layout may also be revisited (hero area, TOC, sections) as part of the
  same pass.
- **New palette**: not locked to the current terracotta (`#e0703c`) accent —
  free to propose a fresh color direction as part of the modernization, but
  should show/explain the reasoning (this is being applied directly per the
  user's answer, not gated on a separate approval step).
- **Manual light/dark theme toggle**: add a visible toggle (persisted, e.g.
  via `localStorage`) in addition to/instead of relying purely on
  `prefers-color-scheme`. Small vanilla JS is fine; no framework.
- Preserve all existing functionality: the client-side search-as-you-type
  filter on the index, the sticky "back to all books" link, the anchor-linked
  table of contents on detail pages, responsive behavior for narrow
  viewports, and the empty/"no summary yet" card state (moot right now since
  all 29 catalog books are finalized, but the code path should stay intact
  for future added books).
- Cover images (both stored JPGs and the deterministic SVG placeholder in
  `src/gttp/covers.py`) must keep rendering correctly in the new layout.
- Accessibility: maintain reasonable contrast in both themes, keep semantic
  HTML, keep the search input labeled, keep focus states visible (don't
  remove outlines without a visible replacement).

## Out of scope

- No new backend/pipeline logic (ranking, synthesis, Reddit fetching) —
  visual/frontend layer only.
- No new JS framework, bundler, or build tooling. Plain HTML/CSS/vanilla JS,
  generated by the existing Python `publish.py` templating approach.
- No changes to the book content/data itself.
- Not fixing the pre-existing, unrelated failing test noted below (flag it,
  don't fix it as part of this task, unless it blocks verifying this
  feature — it doesn't, since it's data-path only).
- No changes to `covers.py`'s network-fetching logic — only how covers are
  displayed/styled.

## Constraints

- Static site generated by `src/gttp/publish.py` (Python), served by a
  minimal container (`entrypoint.sh` runs a static file server over
  `site/`). No SSR, no client routing.
- `gttp build` (no `--only`, no `--force`) is safe to run at any time for
  this feature — it will skip all 29 already-`is_final`-locked books (their
  content won't change) and simply rewrite `site/` from the existing cached
  data plus whatever `publish.py` changes are made. This is the fast,
  zero-API-cost way to iterate on and test the redesign.
- Cover assets already exist under `covers/*.jpg` for all 29 books (or the
  SVG placeholder renders); don't assume covers are missing.
- Keep the whole site self-contained (inline CSS/JS is fine and matches the
  existing single-file-template approach) — no external font/CDN requests,
  to keep it fast and dependency-free like today.

## Acceptance criteria

1. `gttp build` runs cleanly with the updated `publish.py` and regenerates
   `site/index.html` and all 29 `site/books/*.html` pages without errors.
2. The index page renders a visibly modernized layout (typography, spacing,
   color, card treatment) — reviewed visually via the webapp-testing skill
   (screenshot or live browser check) in both light and dark mode.
3. The manual theme toggle is present, switches the site between light and
   dark instantly, and the choice persists across a page reload/navigation.
4. Search-as-you-type on the index still filters the book list correctly.
5. A book detail page renders correctly: hero (cover + title + author + core
   idea), table of contents anchors that scroll to the right bullet, quotes,
   sources, and the "back to all books" link all still work.
6. Responsive check: layout doesn't break at a narrow (~375px) viewport —
   cards/grid reflow, no horizontal overflow.
7. Cover images (both real JPGs and the SVG placeholder path) render
   correctly in the new layout at both the index-thumbnail and detail-page
   sizes.
8. `python -m pytest -q` shows no *new* failures introduced by this change
   (the one pre-existing, unrelated failure —
   `test_build_book_offline_produces_page`, a test-isolation issue caused by
   a real finalized cache entry short-circuiting the offline fixture path —
   is expected and out of scope; do not "fix" it by weakening the new UI code
   or masking the failure).
9. Site is committed and deployed via the `deploy` skill (lab route:
   `docker compose up -d --build` for the `gttp` project), and confirmed
   reachable (HTTP 200) at both `http://127.0.0.1:8100/` and
   `https://gttp.mooseflip.com/` after redeploy.

## Open questions & decisions made

- **Scope**: layout rework is explicitly allowed, not just a CSS refresh
  (user chose "Layout rework too").
- **Palette**: open to a new palette; not required to keep terracotta
  `#e0703c` (user chose "Open to a new palette"). The build subagent/designer
  should pick a considered, current-feeling palette and apply it directly —
  no separate approval gate for the color choice specifically (the overall
  plan does go through this session's own sanity check per the skill, since
  the user chose to skip the plan-approval gate).
- **Theme toggle**: add a manual light/dark toggle (user chose "Add a manual
  toggle"), in addition to keeping `color-scheme: light dark` as the
  sane default before JS runs / for no-JS clients.
- **"Rising trends" interpretation**: left to designer judgment during
  planning — candidates worth considering (not mandates): confident/large
  display typography for headlines, more generous whitespace and rhythm,
  refined card treatments (subtle depth via shadow/border rather than heavy
  skeuomorphism), grid/bento-style layouts for the index, subtle
  scroll/hover/tap micro-interactions, accessible focus-visible styling,
  avoiding generic "AI slop" aesthetics (default Inter/system fonts + purple
  gradients) per this environment's own general design guidance. The
  `ui-designer` skill (if invoked by the planner/executor) and the `dataviz`
  skill's design sensibilities are not directly applicable here (no charts),
  but the general anti-generic-aesthetic guidance from CLAUDE.md-level
  instructions applies.

## Relevant files/areas

- `src/gttp/publish.py` — the entire template: `_HTML_SHELL` (shared
  inline CSS), `_render_index_html`/`_render_index_card` (index page +
  search JS), `_render_book_html` (detail page), `_render_header`/
  `_render_footer`, `_cover_tile`, `_truncate`.
- `src/gttp/covers.py` — `placeholder_svg()` generates the deterministic SVG
  placeholder cover; may need light adjustment if the new design changes
  cover aspect ratio/treatment, but its network-fetch logic is out of scope.
- `static/` — favicons, `logo.png` (header logo), apple touch icons. The
  logo/favicons should be reused as-is (not regenerated) unless the redesign
  specifically requires a different header lockup treatment (e.g. logo
  sizing/placement), in which case only CSS/markup around them changes, not
  the image assets themselves.
- `site/` — generated output (gitignored), not edited directly; always
  regenerate via `gttp build`.
- `tests/test_pipeline.py` — contains `test_render_markdown_has_sections`
  which touches `render_markdown` (Markdown output, not HTML/CSS) — should
  remain passing; not the same code path as the HTML redesign but worth
  confirming it isn't broken.
- `entrypoint.sh` / `Dockerfile` / `docker-compose.yml` — deployment
  mechanics; not touched by this feature except that the final step invokes
  the `deploy` skill against this project (lab route).
